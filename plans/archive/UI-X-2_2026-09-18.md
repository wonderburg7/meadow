Delivered on branch `claude/UI-X-2`. None of H1-H4 below was the actual
cause, and the real one needed the fixture to reproduce Dave's session
rather than a direct jump to 2.2, so this is recorded for the next slice
that meets the same shape of bug.

**The real cause.** `_apply_stage_gate_to_ui` (`challenge_runner.gd`) ends
with an unconditional `main.hud.update_selection(main.selected_bees)`.
`hud.gd::update_selection([])` treats an empty bee list as "nothing is
selected" and hides `command_tray`/`cell_group` to match -- correct for an
actual deselection, wrong for a stage-gate refresh. A fixture that jumps
straight to Challenge 2's stage 2.2 and then selects a cell never exercises
this: the bug only shows when a cell's tray is already open and a stage
boundary is then crossed, which is exactly what teaching text on a live
run does (2.1's own hints run long enough that a player has usually opened
a cell before 2.2 arrives). H1-H3 were ruled out empirically: the Forager
control is unlocked, built and correctly gated -- it is the whole tray that
closes out from under it. H4 was ruled out structurally: `_build_command_tray`
has exactly one caller, `hud.gd::_ready`.

**Fix.** In `_apply_stage_gate_to_ui`, the closing
`main.hud.update_selection(main.selected_bees)` now only runs when there is
a bee selection or no cell selection (`not main.selected_bees.is_empty() or
main.selected_cells.is_empty()`). `set_allowed_role_keys`, called earlier in
the same function, already re-gates an open cell popup in place via
`_apply_cell_popup_gating`; nothing else `update_selection` does applies to
a cell selection.

**A fixture pitfall worth naming.** The headless scenario runner's default
viewport is not one of the three sizes `docs/known-pitfalls.md`/`ui_layout.gd`
call "supported" (800x600 being the floor) -- it is small enough that
`command_tray`'s own width/height floors dominate and every rect assertion
against it reads as a false collapse. Any new `control`/`panel` assertion
against `command_tray` needs an explicit `{"do": "viewport_size", "w": 800,
"h": 600}` (or larger) before it, or it fails for a reason that has nothing
to do with the code under test.

**Drive-by fix, out of this slice's files.** `plans/workstreams.md` (both
the primary checkout's copy and this worktree's) had one row -- this
slice's own, written by `tools/slice.ps1 start` -- with a Windows-1252 em
dash byte (`\x97`) where UTF-8 was expected, which failed
`tools/check_docs.py` inside `verify.ps1` for anyone touching docs on this
branch. Fixed in place (byte replaced with a real UTF-8 em dash); the
`slice.ps1`/PowerShell encoding that produced it is unexamined and likely
still there for the next slice's row.

## UI-X-2 — Challenge 2's cell tray offers a Forager to raise

**Purpose.** Stage 2.2 asks the player to raise a pollen Forager. In Dave's
12 Sep 2026 run a selected cell's tray had no Forager control beside
"Raises:" at all. He confirmed in session on 13 Sep 2026 that the button was
missing, not overlooked. Stage 2.2 cannot be finished the way it is taught.

**Confirmed.** The Raises controls are built once, in
`hud.gd::_build_nursery_controls`, while `allowed_role_keys` is empty, so a
"Forager…" menu (`_make_hatch_menu`) does get built. Its visibility is set by
`_apply_cell_popup_gating()`, which runs on every `_refresh_cell_popup()` and
from both `set_allowed_role_keys` and `set_allowed_designation_keys`, so
**stale gating is ruled out**. Stage 2.2's `unlocked_keys` include
`"forager"`.

**Hypotheses, to test in this order.**
- H1: `"forager"` is not unlocked when the cell is shown.
  `stage_gate._unlocked` lacks it, for example because
  `_apply_stage_gate_to_ui` runs before stage 2.2's unlocks are applied.
- H2: the menu is visible but has no usable rectangle. `hatch_row` is an
  HFlowContainer that "skips sorting while hidden", and the Nursery column's
  equal share may push the menu out of the tray's clipped scroll area.
- H3: another path hides the Nursery column or `hatch_row` in Challenge 2.
  Search for `hatch_row.visible` and the column wrappers' `visible`.
- H4: the control was never built. `_build_nursery_controls` skips any
  `hatch_options()` entry whose role is not in `allowed_role_keys`
  (`continue`, just above `_make_hatch_menu`), and gating afterwards only
  shows or hides what that loop built. Today `_build_command_tray` runs from
  `hud.gd::_ready`, when the list is empty, so this only bites if some path
  rebuilds the tray after the gate is applied -- a Challenge restart or a
  resumed run. Check `_build_command_tray`'s callers before the others; it is
  the cheapest of the four to rule out.

**Also wrong: the check's wording.** C-34 asked for nectar Foragers during
2.1, but 2.1 does not unlock `"forager"`, and `_apply_cell_popup_gating` hides
the colony-default entry whenever keys are restricted. 2.1 therefore offers
nothing to raise by that route. Re-word C-34 before moving it back to ready.

**Owner.** `challenge_runner.gd::_apply_stage_gate_to_ui` decides what is
unlocked, and `hud.gd` only applies it. Keep it that way.
