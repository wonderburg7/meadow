# UI-B-1 — the HUD builds again, and verification boots the game

<!-- CONTEXT: archived-slice | LAYER: on-demand -->
Status: shipped 2026-09-12 | Owner: Dave / Claude Code | Plan: `plans/now/ui.md` | Verified: 2026-09-12

## What Dave reported

12 September 2026, with three screenshots of a maximised 1920x1080 run: "it
seems all panels and labels have gone", and because of that most of the ready
hands-on checks could not be run at all. Alongside it, two smaller findings:
the settings window takes up too much horizontal space, and the Controls
section has unnecessary gaps between its lines.

## Cause

`scripts/hud.gd` called `Rect2.get_closest_point()` in
`_update_stage_marker_arrow`, the edge-arrow helper added by C1-26. Godot 4's
`Rect2` has no such method. That is a parse error, not a runtime one, so it
failed the compile of every script depending on `hud.gd`:

```
SCRIPT ERROR: Parse Error: Cannot find member "get_closest_point" in base "Rect2".
SCRIPT ERROR: Compile Error: Failed to compile depended scripts.
ERROR: Failed to load script "res://scripts/main.gd" with error "Compilation failed".
```

`main.gd` never loaded, so nothing it owns was ever built — every HUD panel,
every readout, every label. The bee identifier labels Dave could still see are
drawn in world space by the bees themselves, which is why the screen was not
simply blank.

It reached `master` and stayed there because nothing in verification opens
Godot. `tools/verify.ps1` runs Python suites, which read GDScript as text and
cannot know that a method does not exist.

## What shipped

1. **The parse error.** `Rect2` has no closest-point helper, so the safe edge
   clamps each axis instead: `clampf(marker_screen.x, safe_edge.position.x,
   safe_edge.end.x)` and the same for y. Same result, a method that exists.

2. **The instrument.** `tools/godot_compile_check.py` boots the project
   headless for 120 frames and fails on any `SCRIPT ERROR`, `Parse Error`,
   `Compile Error` or `Failed to load script` line, or a non-zero exit.
   Booting the real main scene loads `main.gd` and everything under it, which
   is the whole runtime. It is a new `godot boot` stage in `tools/verify.ps1`,
   between the function map and the stage reference, and it skips itself
   (passing) where no Godot binary is installed, so the Codex runtime is
   unaffected. Set `MEADOW_GODOT_PATH` for a non-default install.

   Confirmed both ways: green on the fixed tree, and re-introducing the
   `get_closest_point` call makes the stage print all five error lines and
   exit 1.

3. **The settings window's width.** Measured headlessly: 920px on a 1920px
   viewport. `_build_actions` put the three Triggers buttons in one
   `HBoxContainer`, and a `Button`'s minimum width is its whole label, so
   "Advance Challenge stage", "Fire test warnings" and "Force Challenge 2
   collapse" set the window's minimum width between them. The `ScrollContainer`
   above has horizontal scrolling disabled, so that minimum passed straight up
   to the window. Each long-labelled action and trigger button now gets its own
   full-width row through a new `_add_action_row` helper; Save run and Load run
   keep their shared row. Measured again after: 358px, set by "Force Challenge
   2 collapse" alone.

4. **The Controls gaps.** `_make_controls_help`'s text carried its own
   "Controls" heading — duplicating the section header directly above it — and
   blank lines between its three groups. Both are gone; it is one list in
   reading order.

## Verification

`tools/verify.ps1`: source checks OK, balance tests OK, function map OK,
godot boot OK, stage reference OK.

Hands-on: C-51 (the HUD is back), C-52 (the window's width), C-53 (the
Controls list).

## What this does not explain

`test_scenarios/slice1_smoke_test.json` still returns `status=failed
outcome=max_days` after the fix, exactly as `NEXTSTEPS.md` recorded it on
11 September. The broken compile was not its cause, and that entry stands
unchanged under "Not in the queue, and why".

## Side effect worth knowing

Every headless Godot boot in this repository rewrites `addons/godot_ai/` — the
plugin migrates and reinstalls itself on load, leaving about a hundred
modified and untracked files in the working tree. The headless scenario runner
already did this; the new `godot boot` stage does it too. Nothing in that
directory is part of the game's runtime, and none of it was committed with
this slice.
