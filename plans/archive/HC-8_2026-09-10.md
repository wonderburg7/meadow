# HC-8 — the tray's height matches its content, from the first frame

Archived 10 Sep 2026. Shipped a narrower scope than specified: the
first-open case only. The reselect case this heading originally covered
is now its own slice, HC-16, in `plans/now/hud-controls.md` — see that
heading for the diagnostic evidence behind the split.

## What shipped

`hud.gd::_resize_command_tray` no longer reads
`content.get_combined_minimum_size().y` once, in the same frame as the
rebuild that changed it. Measuring via the headless scenario runner
confirmed the read is genuinely stale on that frame (a traced run: 63 ->
213 -> 291 -> 295 -> 268 for one selection's own settle). `_resettle_command_tray`
now re-applies `UiPanelLayout.apply()` on successive deferred passes until
four consecutive reads of the content minimum agree (capped at 20 passes),
guarded by a generation token so a reselection that lands mid-chain is not
later overwritten by the superseded chain it interrupted. This is proven,
by `tests/fixtures/hc8_tray_first_open_1x.json` and `_2x.json`
(`tests/test_hc8_tray_first_open.py`), for the *first* build of the tray
after a selection — Dave's second report (9-10 Sep 2026): "unnecessary
empty space at the bottom" on first open, and an unneeded scrollbar. Both
are fixed: the tray's height now matches its content within 6px, at 1x and
2x text scale, with no prior selection in the run.

## What did not ship

Dave's *first* report (9 Sep 2026) — "selecting More…, then clicking off
the bee, then clicking back on" — is a **re**selection, and the fix above
does not reliably cover it. Driving the same measurement through a
reselection (with or without `More…` open) found the true content minimum
continuing to change for far longer and far less predictably than the
first-open case: one traced reselection went 386 -> 444 -> 466 and *held*
at 466 under passive observation, but the bounded reapply loop (even with
generous stability requirements, up to 8 consecutive matching reads) settled
at 444 instead — an active-write side effect that reaches a different, also
wrong, fixed point than doing nothing. A separate traced reselection (no
`More…` at all) left the tray 260px+ taller than its content even after 15
settle ticks. No bounded pass-count or signal-driven ("wait for
`minimum_size_changed` to go quiet") strategy tried in this session reliably
found the reselection case's true settled value. This is why HC-16 exists
as its own slice rather than being folded into this one's completion.

## Original specification (as measured against, before the split)

**Reasoning level: medium.** A deferred-layout timing question. The cause is
now strongly indicated but still not measured, and this slice measures first.

**Observable problem, first report (Dave, 9 Sep 2026).** "When selecting more…
in the command tray, then clicking off the bee, then clicking back on, the
command tray takes up a lot of the screen, with a lot of blank space in the
tray." His screenshot shows the tray roughly twice as tall as its content.

**Observable problem, second report (Dave, 10 Sep 2026, C-18).** Two more
sightings of the same panel, neither needing a reselect:

- "When initially starting up the command tray there is unnecessary empty
  space at the bottom. This empty space disappears if you select more… and
  then select more… again so the tray collapses." His screenshot shows a
  selected forager whose Job/Focus/Orders rows end well above the tray's
  bottom edge.
- "Sometimes the command tray uses a scroll bar when there's feasibly enough
  space for it to be expanded."

**What the second report changes.** The first report could only be reproduced
by hand, which is why this slice sat out of the queue waiting on Dave. The
new one cannot be: it happens on the *first* build of the tray for a fresh
selection, and a `More…` toggle — which forces a second layout pass over the
same content — clears it. That is reachable from the headless scenario runner
without a human, so the measurement below is now the implementer's to take
rather than Dave's.

**Established so far.** `more_panel_open` is deliberately sticky (`:389`,
`:2162`), so `More…` reopening on reselect is intended and is not the defect.
The blank width was HC-7's cause and is fixed. The blank *height* is separate:
`ui_panel_layout.gd::apply()` caps the scroll budget at
`content.get_combined_minimum_size().y` and then sets the panel's height from
`panel.get_combined_minimum_size().y`. `hud.gd::_resize_command_tray` zeroes
`command_scroll.custom_minimum_size.y` immediately before that call, so both
reads land in the same frame as the rebuild that changed the content. Godot
invalidates a container's minimum size on a deferred pass, so a minimum read
in that frame can be the previous frame's value — a taller previous selection
gives a taller tray, and a shorter one gives a scrollbar the content does not
need. That single mechanism accounts for all three sightings, and
`_resize_command_tray` is already called deferred for this reason (see its
comment about C-11/C-12), which is evidence the timing is delicate rather
than settled.

**Measurement (10 Sep 2026).** Confirmed stale, but not by a single
predictable frame — see "What did not ship" above.

**Files changed.** `scripts/hud.gd` (the resettle loop), `scripts/scenario_actions.gd`
(a `matches_content` condition on the existing `panel_rect` assertion, reused
rather than adding a second height helper).

**Files that must not be changed.** `scripts/ui_layout.gd` — untouched.

**Check filed.** `tests/fixtures/hc8_tray_first_open_1x.json` and `_2x.json`,
driven by `tests/test_hc8_tray_first_open.py`, covering the first-open case
at both text scales named in the original Check line. The deselect-reselect
case is not covered by an automated check — see HC-16.

reselect case as its own slice rather than claim it as covered.
